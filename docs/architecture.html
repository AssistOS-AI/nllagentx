Architecture and Execution Model

The architecture is organized around a change of authority. Natural language begins as material that can support several interpretations. A coding agent may choose and encode an interpretation, but once the semantic modules are committed, the runtime—not the model conversation—owns execution. Every layer exists to make that transfer explicit without reducing the DSLs to inert configuration.

Authoring crosses the ambiguous boundary once

Before authoring, nllAgent has source bytes, a task instruction, reusable knowledge, and a catalog of constructors and circuits. It does not yet have an executable account of what each relevant sentence means for this task. A generic parser could manufacture records from words, but such records would hide decisions about identity, scope, modality, negation, completeness, and domain vocabulary. Those decisions are precisely where natural-language understanding is difficult.

The coding agent is therefore permitted to use full JavaScript while it creates OntologyJS, IntentJS, LongTextJS, CircuitJS, response policy, and tests. Full JavaScript is not a loophole around the semantic model. The SDK constructors are the boundary through which terms, claims, circuit stages, and results become semantic values. Procedural helpers may calculate, loop, recurse, or call local tools, but semantic effects must still pass through sealed builders, transactions, declared circuit outputs, and validation.

After authoring, ordinary execution imports those modules in a fresh process. The runtime is not allowed to revisit the source prose and make a new undocumented interpretation. If a required concept or behavior is absent, planning produces a typed gap. An explicit coding phase may fill it; deterministic execution may not improvise around it.

The SDK gives every DSL a common semantic algebra

The four main languages share a many-sorted algebra. Broad sorts such as entity, event, state, proposition, claim, quantity, time, evidence, scope, finding, and intent define the kinds of values that can participate in the system. An ontology extends that signature with domain concepts and roles. Calling a constructor such as CustodyTransfer(from(...), to(...)) creates an opaque semantic handle whose sort, ontology identity, roles, and provenance are validated. It does not return a mutable object whose keys happen to look meaningful.

This common signature is what lets the layers connect without sharing storage assumptions. OntologyJS defines a constructor. LongTextJS calls it with ground values from a source. CircuitJS calls the same semantic family with variables or patterns. IntentJS asks for a capability that consumes or produces those meanings. Response code receives a typed finding whose evidence refers back to values created under the same identities.

Identity is semantic rather than accidental object identity. Two mentions with identical text at different source spans remain distinct. Two quantities can canonicalize to the same magnitude and dimension. Claims remain distinct when voice, polarity, scope, grounding, or interpretation differs. Circuit instances include their template, bindings, ontology stack, source snapshot, and interpretation context. These choices allow caching and replay without erasing distinctions that can change a verdict.

A transaction turns authored source meaning into store truth

LongTextJS may construct values procedurally, so the runtime obtains integrity at commit time. A semantic transaction binds itself to the source snapshot, ontology stack, and interpretation context. It collects provisional terms and claims, resolves references, checks sorts and role cardinalities, verifies grounding and coverage, canonicalizes identities, and commits atomically. If the source says a thermometer certificate expired, the resulting claim is not accepted merely because a JavaScript object was created; it must use the correct domain roles, polarity, source span, and ontology identities.

The committed snapshot becomes one logical SemanticStore. The store is a typed attributed term graph with claims, voices, scopes, alternatives, time, quantities, coverage, derived values, findings, and provenance. Its physical indexes are chosen for execution: type and subtype lookup, outgoing and reverse roles, claims by content, source intervals, temporal constraints, quantities, aliases, dependencies, and capabilities. These indexes can be rebuilt from the source modules and disposable caches. They never become a second semantic database that a circuit must understand.

Queries return rows that carry bindings, scope, interpretation conditions, evidence, and completeness metadata. This matters because a join between values from incompatible alternatives must not pretend that both are simultaneously true. It also matters for negative operations: notExists, none, and all require a coverage witness for the same concept, scope, source set, and assumptions. Without it, the result remains unknown or blocked by coverage.

Intent converts purpose into a demand for capabilities

The source interpretation does not determine what the operator wants. The same semantic store can support chronology review, evidence review, policy validation, explanation, repair, or controlled generation. IntentJS records mode, target, concerns, scope, evidence policy, allowed guarantees, output kinds, resource policy, and fallback. It retains the original instruction as provenance while replacing the unstructured prompt with an immutable executable model.

Intent fragments may come from explicit CLI requirements, the task instruction, task-local declarations, agent defaults, source signals, and earlier diagnostics. Their precedence is deterministic. Lexical or structural signals can suggest that a document is normative, scientific, or narrative, but signals do not themselves produce findings. If several domains are plausible, compatible packs can coexist. If no narrowing is justified, the broad fallback executes every compatible circuit in the resolved registry rather than silently doing almost nothing.

The planner begins at the requested outputs and concerns. A finding capability can have several provider circuits; a chosen provider can require several other capabilities. This creates an AND/OR closure problem. Hard incompatibilities, missing ontology, forbidden approximation, and unmet coverage are resolved before cost ranking. Selected providers are ordered by guarantees, completeness, robustness, determinism, reuse, cost, and finally stable identity. The execution plan records not just what will run, but why alternatives were rejected or blocked.

The effective super-circuit remains a composition of small programs

A selected circuit is a contract with one semantic responsibility. It declares requirements, provisions, stages, possible outputs, and optional assurance adapters. One circuit may include another directly, depend on a capability supplied elsewhere, instantiate once per semantic match, request an assurance circuit, or emit a refinement demand. The planner combines those relationships into an effective runtime without copying them into one opaque generated file.

Inside the composition, each declarative stage has typed inputs and outputs. The scheduler builds a dependency graph from those reads and writes. A stable ready queue executes nodes whose inputs are available, validates their outputs, records trace events, and activates newly ready dependents. Procedural stages are macro-nodes: they may contain ordinary algorithms internally, but their external semantic reads, writes, diagnostics, and optional abstract or symbolic summaries remain declared. This is the point at which SOLID ownership becomes operational rather than stylistic: a measurement normalizer, acknowledgement assessor, release-support decision, and response selector can evolve independently while composing through explicit values.

New derived values or per-match circuit instances can extend the graph during an epoch. The instance key prevents duplicate work. When a source unit changes, reverse dependencies identify affected materialization, queries, and descendants; unchanged values may be reused through content identities. A new source snapshot or non-monotone change creates a new epoch rather than mutating the meaning of an old replay.

Concrete execution answers the task; auxiliary interpreters inspect the program

Concrete execution evaluates ground terms from the current store and produces the actual findings or frames. It is the truth-bearing task interpretation. Abstract preflight propagates conservative domains such as possible statuses, evidence states, identity relations, intervals, scopes, and coverage. It can expose that a circuit may reach conflict or that an opaque stage loses precision without enumerating all concrete inputs.

Symbolic execution explores registered branch conditions and decision rows over symbolic values. It is deliberately aimed at semantic circuit constructs rather than arbitrary JavaScript instructions. The constraint kernel can reject infeasible paths and generate bounded microcases around decisions. The resulting path set establishes coverage of the circuit logic; it does not say which symbolic path the current document took. That distinction is why assurance lives in technical artifacts while the public answer is built from concrete findings.

Other compact methods—temporal networks, relation fixed points, finite-domain constraints, monitor-style transition checks, rewriting, decision DAGs, slicing, or bounded repair—are selected by problem shape. They are cooperating kernels over the same handles, not competing stores or a claim of universal theorem proving. Every method advertises applicability and guarantee; approximate output remains separate from four-valued semantic truth.

Response composition is a second program boundary

Semantic execution can legitimately produce more information than the operator should read: internal grounding confirmations, non-applicable branches, secondary satisfied checks, raw paths, and generated frames unrelated to the requested mode. Response circuits operate on immutable findings and frames after semantic execution. Their stages select intent-visible entries, group them, count them, rank attached evidence, and choose a presentation style. The composer validates after every stage that no finding or frame was invented.

The semantic circuit owns the meaning of a requirement and must attach a human-readable statement when it also uses an internal code. The renderer owns fixed grammar such as “the following required conditions are not satisfied.” It cannot discover that THERMOMETER_CALIBRATION_VALID means validity at the transfer time by splitting underscores. The evidence section likewise consumes verified spans selected by the semantic result. It may quote them and mark them as copied source text; it may not search the raw source to repair missing evidence.

Failures remain in the layer that can explain them

A process failure means a command did not complete. A semantic violation means the command completed and found a problem. Unknown means the evidence cannot decide a proposition under the declared scope. Conflict means compatible support and refutation coexist. Blocked ontology, coverage, resource, or method states name the dependency that prevented a requested result. These statuses are kept separate so a tool exit code cannot masquerade as semantic truth.

Every stage records its inputs, outputs, source and ontology dependencies, circuit or method identity, interpretation context, decision reason, cache use, diagnostics, and cost metadata. A backward slice can then show exactly which source claims influenced one finding. Replaying the same modules in a fresh process checks that the result is a consequence of committed code and source snapshots, not of scheduler accident or stale model state. The runtime reference enumerates the implemented constructors and commands; this chapter supplies the causal model that makes those details intelligible.
