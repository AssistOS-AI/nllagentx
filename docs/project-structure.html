The repository layout is not housekeeping around the semantic system; it is part of the semantic contract. A module's directory says whether it is framework machinery, default reusable knowledge, a specialized agent capability, an interpretation of one source, coding-process evidence, or a public result. The runtime and authoring tools use those ownership boundaries when they resolve dependencies and decide what may be reused.

The root separates original contracts from executable implementation

design-specifications/ contains the original DS-000 through DS-019 source contracts. Their content remains preserved rather than rewritten into shorter summaries. docs/specs/ contains the contiguous official set: wrappers around the preserved originals plus additive implementation contracts discovered while building the system. AGENTS.md gives repository-wide coding and ownership rules. observations.md is the review index for decisions that still deserve discussion; insights.md records recurring problem classes observed in real coding-agent work and the regression controls added after them.

tools/ owns deterministic project generators and verifiers: official specifications, HTML, source maps, context catalogs, retained tutorial projections, and contract checks. Generated documentation lives under docs/ with document-relative navigation and project-owned assets. Environment-managed .agents/ may contain maintenance skills available to the current Codex session, but it is not nllAgent product source, is not read by documentation generation, and is not published as a runtime dependency.

The framework defines the languages and their execution, not a particular agent

framework/sdk/ contains the public language surfaces. Core modules define handles, identity, values, collections, logic, provenance, and diagnostics. Ontology, LongText, Intent, Circuit, CNL, agent, and evaluation modules provide fluent builders for their respective contracts. Code here must remain domain-independent enough that a cold-chain task and a narrative-continuity task can use the same transaction, claim, query, decision, evidence, and response primitives.

framework/runtime/ consumes those values. Its store owns transactions, canonicalization, immutable snapshots, and indexes. Query code compiles semantic patterns without exposing physical storage. The planner closes capabilities and explains selection. The scheduler orders declared dataflow. Method kernels implement concrete and auxiliary algorithms. Response composition validates presentation stages. Trace and cache code retain dependencies and replay metadata. This layer may know what a Finding or SourceSpan is; it must not know that one task's thermometer is TH-9.

framework/tools/ connects semantic libraries to the filesystem and coding processes. It resolves agent and task folders, decodes source files, builds run context, invokes adapters, imports semantic programs, writes results, and runs evaluation. framework/cli/ routes user commands to those tools. Keeping the CLI thin matters because evaluation and tests must be able to call the same reusable implementation without scraping terminal text.

Packs and profiles provide reusable defaults before an agent adds a specialty

framework/packs/ contains versioned ontology and circuit modules for common language, logic, elementary domains, reasoning errors, normative structure, and social interaction. A pack can declare concepts, roles, relations, facts, laws, recognition signals, capabilities, requirements, possible statuses, and assurance support. Pack facts are explicitly pack-owned; they are never presented as claims extracted from the current task source.

profiles/ choose coherent pack sets and fallback policies. A minimal profile makes debugging and isolation possible. A broad school profile loads the intended baseline knowledge. A legal or literary profile gives domain-specific emphasis. The profile does not hard-code the final circuit list: IntentJS and capability planning still filter by target, concern, ontology, evidence, output, and guarantee. An agent may provide a local profile when its specialty needs a composition that should travel with that agent.

Project skills teach coding phases how to use the live system

nll-skills/ contains the project-owned authoring workflows. They are not semantic knowledge packs and they are not semantic agents. They teach a coding agent how to create or review architecture, orchestration, SDK primitives, runtime behavior, intent, ontology, LongText grounding, circuits, tests, and evaluations. Each folder owns SKILL.md and workflow.mjs; the latter lets nllAgent resolve dependencies, context, tools, edit roots, and phases programmatically.

The theory these skills need remains authoritative in the DS files and SDK or pack code. A run-local catalog projects the live parts needed for one phase. This prevents ten copied descriptions of the same constructor from drifting while still giving Codex enough context to choose real imports and reuse existing identities.

An agent folder is a reusable semantic product

An agent can live under agents/<name>/, examples/, evaluations/, or an explicit directory supplied to the CLI. Its location may differ, but its ownership model is the same. agent.mjs composes framework packs, a default profile, local modules, and coding policy. ontologies/ defines reusable vocabulary. circuits/ and methods/ define reusable behavior. cnl/ can define agent-specific response composition. profiles/ and lexicons/ refine selection and language. tests/ calibrates these capabilities independently of any one source.

An agent also owns its tasks/ collection and may retain agent-level authoring runs. Code placed at the agent level is available to every task resolved through that agent. That is why a coding phase must not promote a document's named entities or one-off conclusions into the agent merely because doing so makes the current test pass.

A task folder is one request, one source snapshot, and its complete audit trail

task.mjs identifies the task sources, persistent instruction, expected language, and optional profile overlays. source/ retains original files, deterministic decoded source maps, and any task-owned extractor. intent/ owns the executable interpretation of the request. longtext/ owns the executable interpretation of the source, often split into stable units and a deterministic root commit.

ontologies/ and circuits/ appear under a task only when the inherited system cannot represent a needed distinction or operation. cnl/ can add task-local response behavior without changing semantic truth. sdk/ may contain generated facades bound to the resolved ontology identities. tests/ covers this interpretation, including source anchors and local decision behavior. These files are Intermediate artifacts in the tutorials because they are the inspectable bridge from natural-language input to output.

runs/ retains how coding work occurred. Each run has installed skills, generated context, instructions, adapter logs, final response, and checks. results/response.md is the public Markdown CNL answer. Its siblings are technical evidence: execution plan, canonical findings and frames, executable result modules, response-circuit trace, diagnostics, coverage, assurance, binary trace, and artifact manifest. Keeping public and technical results together under the task preserves discoverability without mixing them into one unreadable answer.

The anatomy of a task mirrors the transformation it records

tasks/task-ID/
  task.mjs                 instruction and source ownership
  source/                  original bytes, decoded map, optional extractors
  intent/intent.mjs        requested operation and presentation policy
  longtext/                grounded claims, contexts, alternatives, coverage
  ontologies/              only meanings missing from inherited knowledge
  circuits/                only behavior missing from inherited providers
  cnl/                     optional task response composition
  sdk/                     generated constructor facade for resolved identities
  tests/                   anchors, semantics, decisions, response checks
  runs/run-ID/             skills, live context, Codex process, checks
  results/response.md      primary human-facing Markdown CNL
  results/artifacts.md     index of semantic programs and technical evidence
  results/                 plan, findings, frames, diagnostics, trace, assurance

The order in this tree is causal rather than merely conventional. The source map must exist before exact LongText spans can verify. Ontology identities must resolve before LongText and Circuit modules can import their constructors. Intent must request capabilities before the planner can select providers. Semantic findings must exist before response circuits can render the public answer. Runs and results point back to the canonical modules instead of becoming alternate sources of truth.

Resolution builds one stack from several owners

Every semantic command names an agent through --agent or --agent-dir; task commands additionally use --task or --task-dir. Names resolve through conventional folders, while explicit directories let a caller keep agents elsewhere. Generated import specifiers are calculated relative to each target file and the selected project root, so documentation and semantic code do not need machine-specific absolute URLs.

The runtime begins with mandatory framework language, adds the selected profile's packs, then agent-local ontology and circuits, and finally task-local intent, grounding, and extensions. A later same-identity module may replace an earlier module only where an explicit override contract permits it. Otherwise providers coexist and the planner chooses by capability. Run-local context is informative and never outranks canonical code.

Examples and evaluations preserve different kinds of evidence

examples/ contains committed executable agents and tasks used for explanation and regression. They prove that existing semantic programs run. evaluations/ creates isolated agents and random-ID tasks to measure authoring, semantic accuracy, evidence fidelity, assurance, and replay. A real authoring evaluation proves that target modules were absent, retains the Codex phases that created them, and links metrics to the exact task folder. It therefore carries more process evidence than a stable example.

docs/ projects accepted artifacts into portable pages; it does not become their authority. Tutorial file viewers embed escaped retained content so a static documentation server never fetches arbitrary paths outside its tree. All navigation remains relative. The result is a repository in which a programmer can move from contract, to canonical source, to coding history, to execution evidence without confusing one layer for another.
