nllAgent is a dependency-free Node.js workbench that turns a natural-language request and its source material into inspectable semantic programs, executes those programs, and returns a grounded Markdown CNL answer. It is designed for the awkward middle ground between an ordinary language model and a conventional rules engine: the request may be ambiguous enough to require a coding agent, while the resulting analysis must be explicit enough to test, replay, and review.

The central promise. On first encounter, Codex may interpret natural language and author code. Once that code is accepted, ordinary execution uses the committed .mjs programs and the deterministic runtime; it does not depend on an unrecorded model conversation. The vision contract fixes this boundary, and the specification browser exposes the complete design.

Begin with the question the operator is actually asking

Consider the cold-chain tutorial. The operator is not merely asking the system to find words such as “calibration” or “acknowledgement.” The request is to decide whether a release conclusion is justified by a policy and a concrete transfer record. The source contains requirements, measurements, an expired certificate, an acknowledgement by one party, the explicit absence of acknowledgement by another party, and a conclusion that the sample may be released. A useful answer must keep those roles separate. It must know which sentences state policy, which state observed facts, which deny a fact, which sentence is the conclusion under review, and which missing information should remain unknown.

A single opaque completion can produce a plausible paragraph, but it leaves several questions unanswered. Which source passage justified each conclusion? Did absence of a matching sentence become falsehood by accident? Was a policy requirement confused with an event that actually occurred? Would the same interpretation be used on a second run? Could a programmer reuse the cold-chain vocabulary without also reusing the facts about sample AX-17? nllAgent addresses those questions by making the interpretation itself a set of executable artifacts.

The request contains different kinds of language

The first distinction is between language that teaches reusable behavior and language that belongs to one task. An agent brief describes a durable specialty: the concepts an agent should recognize, the checks it should perform across many sources, the evidence discipline it should follow, and the kinds of answer it should produce. A task instruction selects an operation for one run, such as finding contradictions, checking evidence for a conclusion, or generating an operational procedure. The task sources are the documents whose statements become evidence. They do not share the same semantic status.

The instruction is never inserted into the document as though the document had asserted it. The source is never promoted into default world knowledge merely because one task used it. Reusable distinctions belong to framework packs or the agent folder; source-grounded claims belong to the task. This ownership rule is what lets one reviewed rule-review agent serve many documents without contaminating later tasks with earlier facts. The folder chapter follows that boundary through the repository.

The first encounter leaves programs behind

When the required programs do not exist, nllAgent prepares a coding run rather than pretending that deterministic ingestion understands the document. It resolves the target agent and task, decodes the sources, determines the authoring phase, installs the dependency-closed skill set, and derives compact catalogs from the live SDK, ontology stack, circuit registry, profile, sources, and diagnostics. Codex reads that context and edits canonical JavaScript modules directly. The adapter retains the process, but the natural-language final message from Codex is not treated as the result of the analysis.

Agent-level authoring may create reusable OntologyJS, CircuitJS, response policy, profiles, and tests from an agent brief. Task-level authoring creates IntentJS and LongTextJS from the instruction and source, adding local ontology or circuits only where inherited semantics are genuinely insufficient. These phases are separated because “the source says this happened” and “every future task should understand this kind of event” are different commitments. The authoring chapter explains the complete lifecycle; the coding-agent chapter opens the adapter, skills, context, direct-editing, and verification boundary in detail.

The semantic programs divide interpretation into reviewable responsibilities

OntologyJS supplies the vocabulary and the rules for constructing well-typed semantic values. In the cold-chain case it defines what a custody transfer, calibration validity, acknowledgement, temperature excursion, and release conclusion are, along with the roles that connect them. It does not say that a particular thermometer is valid or that Vale Laboratory acknowledged anything. Ontology code establishes the signature in which those claims can later be expressed.

LongTextJS is the task-owned interpretation of the source. It constructs the particular transfer, readings, thermometer, parties, acknowledgements, policy requirements, and conclusion; it attaches polarity, modality, scope, and exact source spans. “No acknowledgement by Vale Laboratory was attached” becomes a grounded denied acknowledgement rather than a missing keyword. “The calibration certificate expired” becomes a grounded fact about validity at the transfer time. The distinction between a source claim and a pack fact remains visible.

IntentJS is the executable interpretation of what the operator asked to do. It selects the analysis or generation mode, semantic concerns, evidence expectations, assurance, fallback behavior, requested outputs, and presentation policy. The same LongTextJS snapshot could be used by an intent that audits release support, another that checks only measurement normalization, or another that generates a corrective procedure. Intent is therefore a plan demand, not a label guessed from the document.

CircuitJS supplies source-independent behavior. A circuit queries semantic terms, normalizes values, evaluates explicit conditions, preserves unknown and conflict states, and emits findings or typed generation frames with evidence. It reads the semantic store rather than searching raw prose. A response circuit runs later and decides which already-established results should appear, how they are grouped, which exact evidence is quoted, and which controlled-language templates express them. The detailed language surfaces are documented under Semantic programs.

The runtime turns the separate programs into one analysis

Ontology and LongText modules execute through a semantic transaction. The transaction validates sorts, role cardinalities, scope, provenance, interpretation compatibility, and coverage before it commits anything. Accepted values enter one logical SemanticStore. The store may maintain specialized indexes for types, roles, claims, spans, time, quantities, identity, and provenance, but those indexes are implementation views of one semantic authority. A circuit sees typed handles and queries, not storage fields.

IntentJS then becomes a capability demand. The planner examines every resolved circuit from mandatory framework knowledge, the selected profile, the reusable agent, and the task. It rejects incompatible providers, closes required capabilities recursively, detects missing providers or cycles, and records why each candidate was selected, rejected, or blocked. The selected plan is sometimes called a dynamic super-circuit, but it is not a generated monolith. It is a retained composition of independent providers whose contracts and tests remain intact.

The scheduler orders circuit stages by declared reads and writes and runs them deterministically. Concrete execution produces the actual task result. Abstract preflight and symbolic decision coverage may analyze the same circuit model for convergence, possible statuses, decision-row reachability, and bounded path coverage, but they do not replace the concrete verdict. A successful symbolic projection is evidence about the circuit; it is not the answer to the operator.

The system preserves distinctions that ordinary text often blurs

A sentence in a source is normally an attributed claim, not automatically a world fact. Failing to find a claim is not the same as finding its negation; a circuit may conclude from absence only when compatible coverage establishes that the relevant source scope was complete. Two possible references or scopes remain alternative interpretations when choosing one would change the result. Predicate logic retains true, false, unknown, and conflict, while rule findings add states such as not applicable, accepted exception, blocked ontology, or blocked coverage.

These distinctions affect the public answer. In the cold-chain task, the expired calibration and denied receiving-party acknowledgement can support a violation. The excursion path remains unresolved when the source does not establish the condition needed to decide it. The renderer must say those things in domain sentences; it may not expose an implementation constant such as EXCURSION_QUARANTINE_PATH as though that were an explanation.

The public answer is controlled prose, not a debug dump

Semantic circuits emit findings and typed frames. Response circuits receive those immutable values and apply IntentJS presentation policy. They suppress non-applicable and internal checks, retain material results, group compatible findings, count them, select evidence already attached by the semantic circuit, and render results/response.md. They cannot change a status, invent a source span, or repair missing semantics in the presentation layer.

The answer is Markdown CNL: readable sentences with stable markers that a later tool or LLM can filter without parsing arbitrary prose. Requirement codes remain in technical artifacts or explicit machine tags; public requirement lists contain complete domain statements. Generated explanation and copied source text are visibly separated. Every evidence block announces that it is copied exactly, names its source, and reproduces the verified substring rather than asking the reader to resolve character coordinates.

Acceptance depends on executable evidence

Codex completing a process is not proof that the authored semantics are correct. Ontology checks validate identities and frames. LongText checks validate exact anchors, polarity, modality, alternatives, and coverage. Circuit microcases exercise satisfied, violated, unknown, conflict, and not-applicable behavior. Planner tests establish selection and dependency closure. Response tests establish that the public answer contains the selected findings and exact evidence without leaking raw assurance structures.

An evaluation that claims natural-language authoring must also retain the exact brief, instruction, source, installed skills, generated context, Codex logs, created modules, focused tests, execution artifacts, and replay result. A second ordinary run must reproduce the semantic result and public response without Codex. This is why the tutorial pages show Input, Intermediate semantic programs, and Output together: the useful claim is not merely that a model once answered correctly, but that the answer now follows from inspectable code and verified evidence.
