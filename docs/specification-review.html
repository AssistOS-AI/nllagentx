A review identifies affected DS files, code, tests, CLI behavior, HTML pages, tutorials, and unresolved decisions before editing.

Review sequence

  1. Identify the new requirement or observed failure and list every affected DS and implementation surface.
  2. Compare the current contract with actual code and retained evidence.
  3. Update normative Core Content before recording rationale in the next numbered question.
  4. Synchronize code, tests, CLI help, tutorials and other companion documentation.
  5. Regenerate the official DS set and HTML, then run fidelity, behavior and link checks.

Initial specifications remain byte-for-byte preserved. Additive contracts are regenerated from project-owned sources and verified in numeric order. See DS033.
