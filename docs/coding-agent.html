The Coding Agent Inside nllAgent

The coding agent is the component that converts an underspecified natural-language authoring request into canonical semantic code. It is not the semantic agent stored in agents/<name>/, and it is not the deterministic runtime. Codex is the first implementation of this role; CodingAgentAdapter keeps the process boundary replaceable.

Three actors with similar names do different work

A semantic agent is a persistent folder of reusable ontology, circuits, profiles, response behavior, and tests. A coding agent is a process that reads natural language and edits those folders or one task folder. nllAgent itself is the orchestrator and runtime: it resolves ownership, prepares context, starts the coding process when explicitly requested, then validates and executes the resulting modules. Confusing these actors makes it appear either that an agent folder learned by itself or that ordinary execution secretly calls a model.

Codex may run during code ..., real authoring evaluation, or adaptive authoring. It never runs merely because the user requested run, plan, query, source inspection, or unit tests. This makes model use observable and gives ordinary replay a clear meaning.

The adapter creates a process, not a semantic oracle

CodexAdapter invokes the locally installed codex exec command in direct-editing mode. It sets the canonical agent or task directory as the working directory and points Codex to file-based instructions. An optional model identifier is passed through when the operator supplies one; otherwise the local Codex configuration chooses its default. Repository code does not hard-code a time-sensitive model name.

The adapter captures standard output and error, final response, start and finish times, exit status, and changed paths. A zero exit status means the process completed. The adapter does not parse the final prose as a finding, convert it into patches, or decide that tests are semantically sufficient. That deliberate lack of authority is what allows a future adapter to replace Codex without changing the meaning of accepted nllAgent artifacts.

Before Codex starts, nllAgent constructs the world it may rely on

The orchestrator first resolves the project root, target agent, optional task, authoring phase, canonical edit owner, and write lock. It decodes task sources and resolves the active profile plus framework, agent, and task semantic modules. It then loads the selected skill's executable workflow and closes its dependencies. The dependency closure decides both which instructions are installed and which context projections exist.

A run does not receive generic copied theory. SDK_CATALOG.md is derived from live SDK descriptors and shows current imports, signatures, semantics, examples, and diagnostics. ONTOLOGY_CATALOG.md reports the resolved concepts, roles, relations, constructors, and pack ownership. CIRCUIT_CATALOG.md and RESPONSE_CIRCUIT_CATALOG.md report providers, requirements, provisions, stages, statuses, assurance, and local override identities. PROFILE_RESOLUTION.md explains loaded packs and precedence. SOURCE_OUTLINE.md and source tools expose decoded units and exact text. DIAGNOSTICS.md gives the current failures that a review must repair. PROJECT_MAP.md locates canonical owners without assuming a fixed workspace URL.

Only artifacts named by the dependency-closed workflows are generated. This is important in both directions. Missing a declared catalog is a configuration error, because Codex would be asked to code without a promised dependency. Generating every catalog for every phase would create a large, misleading context and make workflow manifests descriptive rather than executable.

A skill is both a reading contract and a machine-resolved manifest

Each nll-* skill has two synchronized parts. SKILL.md tells Codex when the skill applies, which design boundaries matter, how to inspect the current state, which artifacts it may create, what tests it must write, and what evidence completes the phase. workflow.mjs declares the same responsibility in a form nllAgent can resolve: design specifications, context artifacts, CLI tools, dependencies, edit roots, and lifecycle phases.

Dependencies create a meaningful order rather than a flat pile of prompts. The ontology skill depends on SDK knowledge because it must use real constructors. LongText work depends on intent and ontology because grounding must reflect both the operation and the available semantic signature. Circuit work depends on runtime and ontology because it must choose query, decision, procedural, or assurance primitives that the local runtime actually implements. Testing and evaluation close the chain without giving test execution permission to start Codex implicitly.

The generated INSTRUCTIONS.md makes that order explicit: installed dependency skill contracts first, then the selected DS files, then the context artifacts that were actually generated, followed by the objective, edit root, and checks. The adjacent run.mjs records the adapter, working directory, skill IDs, owner, and deterministic owner-level command. A reviewer can therefore reconstruct what Codex was told without relying on ephemeral API messages.

Codex edits the source of truth directly

The canonical working directory is the agent when the phase creates reusable knowledge and the task when it interprets one source. Codex may inspect any relevant local code, but the workflow's edit roots communicate which ownership boundary it must preserve. It writes ordinary .mjs modules using SDK builders, imports semantic identities from resolved ontology facades, and writes node:test checks beside the owner. nllAgent does not ask for JSON and later translate it into DSL code; such translation would erase the design choices and make the retained model output the hidden authority.

During architecture work, Codex decides which modules and capabilities are needed and where they belong. During ontology work, it designs stable concepts, roles, cardinalities, lexicalizations, and constructor facades. During circuit work, it implements source-independent behavior and its satisfied, violated, unknown, conflict, and not-applicable microcases. During task intent work, it preserves the original instruction and declares presentation policy. During LongText work, it uses source inspection tools to choose exact spans and constructs claims, contexts, alternatives, and coverage. Review work receives failures and trace slices and may repair the canonical modules; it cannot weaken the acceptance gates that requested the review.

Tools give the coding agent observations, not answers to copy

CLI tools reduce uncertainty about the local system. Catalog commands reveal which constructors and providers exist. Source commands expose exact decoded evidence. Intent and plan commands explain selection. Ontology, LongText, and circuit checks expose typed contract violations. Trace commands isolate the dependencies of a bad finding. These tools do not author semantic meaning on Codex's behalf; they make the state that constrains authoring observable.

# Build the dependency-closed skills and live context for an intent-authoring phase without starting Codex.
node nllAgent.mjs context build --agent-dir path/to/agent --task-dir path/to/task --phase intent

# Inspect the exact skills, DS contracts, catalogs, owner, and checks placed in that prepared run.
node nllAgent.mjs context show --agent-dir path/to/agent --task-dir path/to/task --phase intent

# Start the explicit Codex intent-authoring phase against the canonical task directory.
node nllAgent.mjs code intent --agent-dir path/to/agent --task-dir path/to/task

# Execute the authored semantic programs afterward without invoking Codex.
node nllAgent.mjs run --agent-dir path/to/agent --task-dir path/to/task --assurance all

Verification is deliberately split across three viewpoints

First, Codex runs the focused discovery and validation commands named by its skill while it works. This catches errors quickly and lets it iterate in context. Second, the generated run manifest names an owner-level fast test that nllAgent can execute after the process. Third, evaluation or adaptive authoring applies phase-specific acceptance: it compares before and after paths, imports the new code, verifies ontology closure and anchors, runs focused tests, executes real planning and circuits, checks public CNL and exact evidence, and requires replay.

These layers answer different questions. Codex's check asks whether the current edit appears coherent. The owner test asks whether the canonical folder still satisfies its local contract. Evaluation asks whether natural-language authoring actually created the requested behavior and whether that behavior survives model-free execution. A phase can pass the first and fail the third; the retained failure is useful evidence about the coding workflow rather than something to hide.

Retained runs make the coding process auditable

Every run directory keeps installed skills, generated context, instructions, process logs, final response, timings, exit status, before/after artifact inventory, and check results. In a real authoring evaluation, the agent brief and task sources are retained outside those run directories as input evidence. The canonical modules live under the agent or task. Results and replay live under the task. These separate locations let a reviewer answer four different questions: what Codex was asked, what it knew, what it changed, and what the independent runtime subsequently proved.

The skill workflow chapter exposes every live manifest and its exact tool set. The testing and evaluation chapter explains the independent gates. The tutorials show the application-facing result after this process has produced accepted code.
